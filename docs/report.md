## Используемые модели

Llm - основная (отвечает на вопрос с обогащенным контекстом)
```
LOCAL_MODEL=google/gemma-4-e2b
```

Llm - судья 
```
JUDGE_MODEL=google/gemma-4-26b-a4b-qat
```

Thinking - надо отключать для обеих моделей в LmStudio руками (через запрос нельзя). 
```
LOCAL_REASONING_EFFORT= - не ставим иначе отклоючение thinking не поможет
```

Настройки gemma моделей:
```
Temperature: 1
Top K Sampling: 64
Repeat Penalty: 1.1
Top P Sampling: 0.95
```
Температура высоковата. Не знаю в чем причина, но при низких температурах больше вероятность что модель зациклится при ответе. Поставил 1 чтобы не рисковать (+ Repeat Penalty: 1.1).
(Зацикливание не зависит от контейнера для инфиренса: LlmStudio/Ollama/Omlx)

Эмбедер
```
EMBEDDING_MODEL=BAAI/bge-m3
```

Реранкер
```
RERANK_MODEL=BAAI/bge-reranker-v2-m3
```

## Гибридный поиск с реранкингом и разным MMR

Запуск
```
MMR_THRESHOLD=0   uv run python -m eval.run full --judge --hybrid --rerank --mmr2 --name hybrid-mmr00
MMR_THRESHOLD=0.3 uv run python -m eval.run full --judge --hybrid --rerank --mmr2 --name hybrid-mmr03
MMR_THRESHOLD=0.6 uv run python -m eval.run full --judge --hybrid --rerank --mmr2 --name hybrid-mmr06
```
Результаты с метриками: 
- [docs/eval/hybrid-mmr00.md](eval/hybrid-mmr00.md)
- [docs/eval/hybrid-mmr03.md](eval/hybrid-mmr03.md)
- [docs/eval/hybrid-mmr06.md](eval/hybrid-mmr06.md)


Как повлияло в сравнении с hybrid без mmr:

| Метрика | hybrid | mmr 0.6 | mmr 0.3 | mmr 0.0 |
|---|---|---|---|---|
| page_hit_rate | 0.684 | 0.684 (0%) | 0.579 (−15%) | 0.474 (−31%) |
| mrr | 0.833 | 0.829 (−0.5%) | 0.803 (−4%) | 0.816 (−2%) |
| precision@k | 0.400 | 0.379 (−5%) | 0.263 (−34%) | 0.200 (−50%) |
| fact_hit_rate | 0.895 | 0.868 (−3%) | 0.737 (−18%) | 0.640 (−28%) |
| citation_honesty | 0.907 | 1.000 (+10%) | 0.902 (−0.6%) | 1.000 (+10%) |
| answered_rate | 0.895 | 0.842 (−6%) | 0.842 (−6%) | 0.789 (−12%) |
| faithfulness | 0.930 | 0.904 (−3%) | 0.934 (+0.4%) | 1.000 (+8%) |
| correctness | 0.447 | 0.409 (−8%) | 0.404 (−10%) | 0.316 (−29%) |
| seconds_per_question | 3.637 | 5.033 (+38%) | 4.928 (+35%) | 5.359 (+47%) |
| разных страниц в выдаче | 4.40 | 4.60 | 4.95 | 4.95 |

`citation_format` во всех четырёх прогонах 0.000, `refusal_rate` и `judge_parsed` — 1.000.

Приём работает по назначению: 
- разных страниц в выдаче в среднем больше (4.40 → 4.95), то есть при `TOP_K` = 5
почти каждый фрагмент с отдельного листа. Но метрики из-за этого падают: `precision@k` вдвое ниже,
`fact_hit_rate` просел с 0.895 до 0.640 — нужный текст перестаёт доходить до модели.

Причина улучшения `faithfulness` до 1.000 и `citation_honesty` до 1.000 при mmr=0: 
- модель отвечает реже (`answered_rate` 0.789), а не выдумывает меньше. Меньше ответил - меньше ошибся.

Вывод: техники дали результат на уровне шума либо немного просели, а время
на вопрос выросло в 2.5 раза. Лучший по сути прогон — baseline + фильтры по году.

Т.е. advanced RAG не помог а только ухудшил результат.

Почему такой результат? Возможно не каждый базовый RAG можно улучшить.

На первых тестах во время разработки у меня было только 11 вопросов и чанкинг нарезкой с перекрытием (размер чанка был меньше - 512 против 1024).
По мере добавления новых техник к baseline - на уровне шума, но метрики росли и hybrid+reranking выигрывал заметно.

Но потом я заменил нарезку чанков на нарезку по структуре - от этого скакнули вверх метрики baseline а advanced-техники перестали давать преимущество.

Также возможно что во время экспериментов с Neo4j (которые я выкинул в итоге) - где-то что-то было сломано.

**В чем главная сложность извлечения точных номеров страниц из PDF-файлов (например, сбивается ли нумерация из-за оглавления)?**

Сложность написать парсер и вычленить реальные номера страниц из pdf.
Если нужны реальные страницы (проставленные в документе) а не физические, то в зависимости от pdf они могут стоять на разных местах, а также pdf могут содержать как обычные A4 страницы, так и страницы разворота.

---

**Прочие сложности**

- Из коробки фреймворка ничего не работает - все равно надо писать все самому когда доходит дело до реальных документов. 5 строк кода которые продает фреймворк llamaindex для Advanced RAG работают только на игрушечных примерах.
- Pdf парсить сложнее текстового, например: с графиками разного рода, диаграммами и картинками, разными разворотами страниц. Если в базе уникальные pdf то либо терять информацию либо под каждый документ писать кастомный парсер. *"О, ну вы возьмите vision модель и пусть она распознает скриншоты - у нас для этого куча прекрасных фреймворков"* - ага и получим кучу опечаток, искажений данных и галлюцинаций от этой модели  на пустом месте хотя скриншот качественный и чистый (Пример ошибки: "1 Января" -> "Лянваря").
- Neo4j + хелперы llamaindex для граф-RAG - не работает из коробки - не повышает качество. Пробовал в разных вариантах применения графа и по разному строил сам граф: как с LLM так и детерминировано через парсинг отчета. Максимальный результат: около baseline (+/-). Из репозитория удалил код, чтобы не отчитываться по нему (задание явно не требует). Для качественной реализации нужно быть погруженным в предметную область и знать какие типовые запросы будут приходить в RAG. Ни того ни другого у меня нет, отказался.
