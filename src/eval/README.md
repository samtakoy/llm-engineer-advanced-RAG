# Прогон контрольных вопросов

Набор из 11 вопросов к отчётам эмитента и метрики к ним. Нужен, чтобы сравнивать выдачу
базового RAG с выдачей после добавления практик Advanced RAG на одних и тех же вопросах.

Вопросы и эталоны лежат в [questions.yaml](questions.yaml) — это единственный источник
правды, ничего дублировать не нужно.

## Запуск

```bash
uv run python -m eval.run retrieval        # только поиск, ~13 секунд
uv run python -m eval.run full             # поиск и ответы модели, ~5 минут
uv run python -m eval.run full --judge     # то же плюс оценка ответов моделью, ~8 минут
```

Техники поиска включаются флагами:

```bash
uv run python -m eval.run retrieval --filters          # отбор по тегам вопроса
uv run python -m eval.run retrieval --rerank           # cross-encoder из RERANK_MODEL
uv run python -m eval.run retrieval --hybrid           # вектор плюс лексический BM25
uv run python -m eval.run retrieval --mmr              # разбавление выдачи, вес из MMR_THRESHOLD
```

Флаги складываются: прогон с флагом и без него под разными именами и даёт сравнение.

Имя снимка задаётся `--name`, отчёты пишутся в `docs/eval/<имя>.md` и `<имя>.json`.
Markdown — для чтения, json — чтобы сравнить два прогона.

В каждый снимок записываются настройки, при которых он снят: модель, модель судьи,
эмбеддер, размер чанка, перекрытие, top-k. Прогон **отказывается писать поверх снимка
с другими настройками** и предлагает взять другое имя — иначе прогон на новой модели
затёр бы предыдущий, а снимался тот минутами. Пересъёмка с теми же настройками разрешена.

Так снимки на разных моделях ложатся рядом:

```bash
uv run python -m eval.run full --judge --name gemma-26b
uv run python -m eval.run full --judge --name gemma-4b
```

Режим `retrieval` не обращается к модели вообще, поэтому идёт секунды. На нём и подбираются
настройки поиска: перебрать `TOP_K` или включить реранкер и сразу увидеть цифры. Полный
прогон нужен для отчёта и для метрик, которые считаются по тексту ответа.

## Метрики

Первые шесть считаются без модели и от прогона к прогону не плавают — на них и сравниваются
техники поиска. Последние три зависят от судьи и гуляют в пределах сотых: сдвиг меньше 0.1
считать шумом, а не эффектом.

Рядом с каждой метрикой печатается счёт и номера вопросов, которые не зачлись:
`correctness 0.800 · 8 из 10 вопросов · не зачлось: 7, 9`. Номер вопроса — это адрес,
по которому открывают отчёт и смотрят, что пошло не так.

| Метрика | Смысл |
|---|---|
| `page_hit_rate` | Доля вопросов, где выдача покрыла весь эталон по страницам |
| `page_hit_rate@3` | То же по первым трём фрагментам: более жёсткая планка |
| `mrr` | Средний обратный ранг первой эталонной страницы: 1.0 — первое место, 0.5 — второе |
| `fact_hit_rate` | Доля эталонных подстрок, дошедших до модели в тексте выдачи. Строже, чем `page_hit_rate`: см. ниже |
| `citation_format` | Доля ссылок, записанных в формате, который требует промпт. Без неё модель, ссылающаяся не по форме, неотличима от молчащей |
| `citation_honesty` | Доля ссылок, которые указывают на существующую страницу, побывавшую в контексте. Прямое измерение галлюцинации источников |
| `answered_rate` | Доля вопросов, где модель ответила, а не сказала «не знаю» при наличии ответа |
| `refusal_rate` | Доля вопросов-провокаций, где модель верно отказалась отвечать |
| `faithfulness` | Доля утверждений ответа, которые следуют из контекста |
| `correctness` | Доля фактов эталона, попавших в ответ |
| `judge_parsed` | Доля разобранных ответов судьи. Если она заметно ниже единицы, остальные оценки судьи ничего не стоят |

### Где здесь recall

Привычный recall у нас на двух уровнях под своими именами:

- `fact_hit_rate` — recall контекста, он же `context_recall` в ragas: нужный текст дошёл до модели;
- `correctness` — recall ответа: нужные факты модель действительно назвала;
- `page_hit_rate` — то же, что первый, но грубее: по страницам, а не по фактам.

Разрыв между `fact_hit_rate` и `correctness` показывает, где узкое место. Если первый заметно
выше — поиск приносит больше, чем генерация использует.

`context_precision` не считается: при `TOP_K` = 5 и эталоне в одну-две страницы она упирается
в 0.2–0.4 и почти не меняется, а качество ранжирования уже меряет `mrr`. Осмысленной станет
с реранкером, когда из двадцати кандидатов будут отбираться пять.

## Как считает судья

Судью не просят назвать балл: локальная модель числа не калибрует, и «0.73» нельзя
проверить. Вместо этого он раскладывает тексты на отдельные утверждения и отвечает по
каждому «да» или «нет», а балл получается делением:

```
faithfulness = подтверждённых утверждений ответа / всего утверждений ответа
correctness  = найденных фактов эталона / всего фактов эталона
```

Разбора два, и они идут в разные стороны: первый — от ответа к контексту, не выдумал ли
ассистент лишнего; второй — от эталона к ответу, не упустил ли он нужного. Ответ, где
названы три риска из четырёх, получает faithfulness 1.00 и correctness 0.75: ничего не
выдумано, но неполно. Двоичный вердикт сплющивал бы это в «неверно» — то же самое, что
не назвать ни одного.

Отказ отвечать даёт faithfulness 1.00: фактов не приведено, значит и не выдумано ничего.
Несошедшиеся пункты перечисляются в отчёте поимённо — оценка без разбора непроверяема.

На вопрос-провокацию судья не вызывается: его эталон — сам отказ, раскладывать такой
эталон на факты бессмысленно, а верность отказа меряет `refusal_rate`.

Модель судьи задаётся переменной `JUDGE_MODEL`:

```bash
JUDGE_MODEL=glm-4.7-flash-mlx    # пусто — судит та же модель, что отвечает
```

Судить своей же моделью методологически слабее, чем независимой, зато воспроизводимо
и бесплатно. Смена судьи сдвигает `faithfulness` и `correctness`, поэтому снимки, снятые
разными судьями, между собой несравнимы — модель судьи и записывается в снимок.

## Диагностика: разных страниц в выдаче

Печатается отдельной строкой под итогами, в сами метрики не входит. Показывает, по
скольким разным страницам разошлись `TOP_K` фрагментов. Значение 4.45 при `TOP_K` = 5
означает, что примерно в половине вопросов два фрагмента взяты с одного листа.

Это не дубли: страница режется на несколько фрагментов, и текст в них разный, отсекать
нечего. Решения на основе этого числа сейчас не принимаются — оно нужно, чтобы увидеть
эффект MMR, когда тот появится в поиске (шаг 5 роадмапа). Не путать с `mrr`: MMR —
приём поиска, MRR — метрика ранга.

## Страница против фрагмента

Страница режется на несколько фрагментов, и в выдачу попадает фрагмент, а не вся страница.
Поэтому `page_hit_rate` показывает попадание, даже когда пришёл фрагмент без искомого факта.

Это закрывает `fact_hit_rate`: у каждого вопроса в `questions.yaml` заданы `expected_snippets` —
дословные куски, которые обязаны оказаться в тексте выдачи. Проверка идёт подстрокой по
склеенному тексту фрагментов, пробелы схлопываются.

Расхождение двух метрик и есть диагноз:

| Вопрос | `page_hit_rate` | `fact_hit_rate` | Что означает |
|---|---|---|---|
| 7. Таблица конкурентов | 1.0 | 0.0 | Страница нашлась, таблица в пришедший фрагмент не попала |
| 9. Клиника МОНИКИ | 1.0 | 1.0 | Поиск сработал, текст испорчен разбором PDF |

Подстроки заданы дословно по индексу, а не по смыслу: в таблице стоит `115.9` с точкой,
а не `115,9`. Новую подстроку перед добавлением проверять на вхождение в корпус, иначе
метрика будет молча занижена. От размера чанка подстроки не зависят — в отличие от
эталонных фрагментов, которые пришлось бы переразмечать после каждой смены `CHUNK_SIZE`.
